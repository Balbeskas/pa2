##  1. Ключевые характеристики качества ISO/IEC 25010

1. **Функциональная пригодность (Functional Suitability):** Система полностью обеспечивает корректную загрузку корпоративных документов, версионирование файлов (без затирания оригинала), наложение и валидацию ЭЦП, а также полнотекстовый поиск (FTS) по содержимому текстовых документов и PDF.
2. **Надежность (Reliability):** Отказоустойчивость хранилища за счет репликации данных и изоляции поисковых индексов. При сбое индексатора (например, Elasticsearch) система сохраняет базовый доступ к файлам по реляционным метаданным, а очередь обработки восстанавливается после перезапуска сервиса.
3. **Производительность и эффективность (Performance Efficiency):** Время отклика API поиска не превышает 200 мс за счет предварительного кэширования. Использование потоковой загрузки файлов (Stream API) предотвращает избыточное потребление памяти (RAM) при парсинге тяжелых PDF-документов.
4. **Удобство использования / UX (Usability):** Интуитивный веб-интерфейс оператора архива с подсветкой синтаксиса найденных фрагментов текста. Статус верификации ЭЦП отображается контрастными графическими маркерами (валидна/невалидна), а история версий доступна в один клик.
5. **Безопасность (Security):** Разграничение доступа на основе ролей (RBAC), шифрование трафика (HTTPS/TLS) и хранение контрольных хэш-сумм (SHA-256) для контроля целостности файлов. Защита закрытых ключей ЭЦП; строгий запрет на хранение секретов внутри репозитория.
6. **Сопровождаемость (Maintainability):** Архитектура системы разделена на слабосвязанные модули (сервис хранения, сервис индексации, криптографический шлюз). Код покрыт автотестами, а конфигурации вынесены за пределы бинарных файлов, что упрощает багфиксинг.
7. **Совместимость (Compatibility):** API архива поддерживает обратную совместимость версий. Старые клиенты могут запрашивать документы без поддержки FTS, а новые модули корректно взаимодействуют с историческими версиями API криптошлюза благодаря стандартизированным структурам JSON/REST.
8. **Переносимость (Portability):** Полная контейнеризация приложения с помощью Docker. Система разворачивается идентично как в локальном окружении разработчика, так и в изолированном корпоративном облаке (on-premise) независимо от базовой операционной системы.

##  5. Схема ветвления Git и модель командной работы

Командная разработка задачи «Полнотекстовый поиск» базируется на модели **GitHub Flow**, где стабильный код всегда находится в `main`, а новые фичи разрабатываются в изолированных ветках.

### Жизненный цикл ветки `feature/fts-search`:
1. **Инициализация:** Разработчик скачивает актуальный `main` и создает локальную ветку:
   ```bash
   git checkout main
   git pull origin main
   git checkout -b feature/fts-search
   ```
2. **Разработка:** Реализуется логика индексации и поиска. Изменения фиксируются коммитами:
   ```bash
   git add .
   git commit -m "feat: добавить полнотекстовый поиск на базе Elasticsearch"
   ```
3. **Публикация:** Ветка отправляется в удаленный репозиторий:
   ```bash
   git push origin feature/fts-search
   ```
4. **Pull Request (PR):** Создается PR в ветку `main` через интерфейс GitHub. 
5. **Интеграция и Ревью:** Запускаются автоматические тесты (GitHub Actions CI). Коллеги проводят код-ревью. 
6. **Слияние:** После успешного тестирования и апрувов PR закрывается методом *Squash and merge*, а ветка удаляется.

##  6. Конфигурационная модель (Configuration as Code)

**Configuration as Code (CaC)** — это практика, при которой настройки ИС описываются в виде структурированных текстовых файлов, хранятся в системе контроля версий и проходят аудит наравне с кодом приложения.

Пример конфигурации (`appsettings.json`) для управления инфраструктурой архива:
```json
{
  "StorageSettings": {
    "LocalStorageRoot": "/var/storage/digital_archive",
    "AllowedExtensions": [".pdf", ".docx", ".xlsx"],
    "MaxFileSizeMb": 50
  },
  "FtsEngineSettings": {
    "Provider": "Elasticsearch",
    "NodeUrl": "http://localhost:9200",
    "DefaultIndexName": "archive_documents_index",
    "EnableHighlighting": true
  },
  "CryptographySettings": {
    "RequireValidSignature": true,
    "AllowedThrustedRootsThumbprints": [
      "A1B2C3D4E5F67890J1K2L3M4N5O6P7Q8R9S0T1U2"
    ]
  }
}
```
*Пояснение:* Настройки не жестко зашиты в код, а вынесены в конфигурацию. Это позволяет изменять параметры среды (например, переключать URL-адрес поискового движка) без перекомпиляции архивного приложения.

##  7. Решение интеграционных кейсов / конфликтных ситуаций

### Кейс А: Возникновение конфликта слияния (Merge Conflict)
Если два разработчика одновременно изменили одни и те же строки конфигурационного файла, Git останавливает слияние. Алгоритм действий:
1. Загрузить актуальное состояние целевой ветки: `git checkout main && git pull`.
2. Перейти в свою ветку фичи и запустить слияние: `git checkout feature/fts-search && git merge main`.
3. Открыть файлы с маркерами конфликта (`<<<<<<<`, `=======`, `>>>>>>>`) в IDE.
4. Совместно со вторым автором кода определить корректный вариант настроек и удалить маркеры разметки Git.
5. Зафиксировать разрешение конфликта: `git add . && git commit -m "fix: разрешить конфликт слияния в конфигурации хранилища"`.
6. Отправить чистую ветку на GitHub: `git push origin feature/fts-search`.

### Кейс Б: Обнаружение незащищенных секретов в коде
Если в коммит случайно попал приватный ключ ЭЦП или пароль доступа к Elasticsearch:
1. **Немедленный отзыв:** Секрет признается скомпрометированным. Пароль или ключ аннулируются и перевыпускаются на сервере.
2. **Очистка истории Git:** Обычный новый коммит поверх старого оставляет секрет в истории. Используется специализированная утилита `git-filter-repo` или `BFG Repo-Cleaner` для полного удаления строки или файла из истории всех прошлых коммитов репозитория.
3. **Безопасное перераспределение:** Пароли и ключи переносятся в Переменные окружения (Environment Variables) сервера или хранилище секретов (GitHub Secrets / HashiCorp Vault), а скомпрометированный файл вносится в `.gitignore`.

##  8. Выводы

Системы контроля версий (Git) и подходы **Configuration as Code** выступают главным фундаментом обеспечения надежности разрабатываемой АИС «Цифровой архив документов». 

Использование модели **GitHub Flow** изолирует разработку сложных подсистем (таких как полнотекстовый поиск), предотвращая внесение багов в стабильный продакшн-код. Обязательный этап Pull Request гарантирует кросс-ревью кода и автоматический контроль безопасности (поиск утечек ключей ЭЦП, валидация метаданных через CI). В свою очередь, концепция **Configuration as Code** исключает риски рассинхронизации сред («на моем компьютере все работало»), делая развертывание архива документов предсказуемым, прозрачным для аудита и устойчивым к инфраструктурным сбоям.
